Para le punto 2.1 cuando dices:
2.1. Criterios de priorización
Para cada requisito vamos a valorar tres ejes:
•	Impacto (en el objetivo de Mexus):
•	Alto: sin esto, la app no cumple su propósito (grabar llamadas, seguridad mínima).
•	Medio: mejora mucho la utilidad, pero la app “funciona” sin ello.
•	Bajo: nice to have, comodidad o estética.
•	Esfuerzo:
•	Estimado en puntos Fibonacci: 1, 2, 3, 5, 8, 13…
•	Riesgo:
•	Técnico: APIs Android, permisos, posibles incompatibilidades.
•	Legal/ética: textos de consentimiento, protección de datos.
•	Lo marcaremos como Bajo / Medio / Alto.
Regla tentative para MoSCoW:
•	Must: impacto alto, riesgo asumible, esfuerzo razonable para v1.
•	Should: impacto medio/alto, pero puede ir a v1.1 si aprieta el calendario.
•	Could: impacto medio/bajo y riesgo bajo.
•	Won’t (this time): explícitamente fuera de la primera release.
¿Te parece bien esta tríada Impacto–Esfuerzo–Riesgo como base para MoSCoW?
SI, PERO CON EL MATIZ DE QUE NOS VAMOS A CENTRAR SÓLO EN Must, SOLO LO QUE TIENE QUE TENER PARA LA v1

3. Porcentajes de esfuerzo por fase
Tomando como guía buenas prácticas de proyectos tipo DSDM/Agile, podríamos plantear algo así para v1 Mexus:
•	Análisis y diseño: 15–20%.
•	Desarrollo (código nativo + UI): 45–55%.
•	Pruebas (manuales + ajustes): 20–25%.
•	“Operación” / documentación / puesta en marcha: 10–15%.
Luego lo afinamos cuando tengamos el backlog y los puntos Fibonacci, pero ¿te encaja este rango de partida?

DE PARTIDA PREFIERO ASIGNAR 50-60% A DESARROLLO Y 20-25% A ANÁLISIS Y DISEÑO
